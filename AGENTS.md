# Vimac

Keyboard-driven navigation of the macOS GUI, driven by the Accessibility API.
A fork: it ships no prebuilt app and requires macOS 15 or later.

`README.md` covers building and the user-facing workflow; `docs/manual.md` is the manual.
This file records what those don't: the conventions to follow and the traps to avoid.

## Verifying changes

Use the `Makefile`, not raw `xcodebuild` — the scripts behind it set the signing, bundle-id, and `UserDefaults` isolation that a bare invocation misses.

```
make build       # Debug build under build/
make test        # Packages/ tests, then the VimacTests bundle
make run         # launch the Debug build
make install     # build Release and install to /Applications
make screenshot  # launch, open Preferences, capture to tmp/screenshots/
```

`make bootstrap` installs the Ruby gems, and is only needed for the fastlane lanes (`build`, `test`, `screenshot`) that wrap the same scripts.
Swift dependencies resolve on their own.

The UI-test target is skipped by `make test`: it needs Accessibility permission granted to the test runner.
Run it by hand with `xcodebuild test -only-testing:VimacUITests` once that is granted.

## Layout

`ViMac-Swift/` is the app; `ViMac-SwiftTests/` its unit tests; `ViMac-SwiftUITests/` the UI tests.

`Packages/` holds local Swift packages for logic that stands apart from the app — currently `HintEngine` (hint labels and the keystroke matcher).
Each carries its own tests.
`make test` runs them through SwiftPM before the app bundle, because `xcodebuild -only-testing:VimacTests` cannot reach a package's test target.

Prefer a package over the app target for anything that doesn't need AppKit, the Accessibility API, or app state: it tests in a second instead of a minute.

## Conventions

Tests use **Swift Testing** — `@Suite`, `@Test`, `#expect`.
XCTest survives only in the UI-test target, which has no alternative.
Name a case after the behaviour it pins down, not the step it performs.

`Vimac.xcodeproj/project.pbxproj` is hand-maintained; there is no XcodeGen.
Adding or removing a source file means editing it directly.
Entries for Swift package products follow the `A0C50000...` UUID convention already in the file.
After editing it, `plutil -lint` the file and run `make build` — a malformed project file fails in ways that don't point back at the edit.

Settings go through `Setting`/`SettingsStore` (`ViMac-Swift/Settings/Model/`), which falls back to the default whenever what is stored is missing, of the wrong type, or fails the setting's own validator.
Don't read `UserDefaults` directly.

Dependencies are AXSwift, MASShortcut, and RxSwift 5.1.1.
The RxSwift version is old and the codebase leans on it heavily; treat a migration as its own project, not a drive-by.

## Traps

The app needs **Accessibility** permission to do anything at all, and `make screenshot` additionally needs **Screen Recording** for the terminal running it.

Dev and test builds append a suffix to the bundle id (`-dev`, `-test`) and the app name, so they don't trip `AppDelegate.isDuplicateAppInstance()` against an installed copy.
`make install` refuses to install anything carrying a suffix.

Tests reach the settings layer through the `SettingsStorage` protocol, standing `InMemorySettingsStorage` in for `UserDefaults`; the `-test` bundle id keeps whatever does hit the real defaults in its own domain.
Keep both — a test that reads `UserDefaults.standard` under the shipping bundle id would rewrite the user's own shortcuts.

Signing settings live in `Config/Project.xcconfig`.
Override `DEVELOPMENT_TEAM` in `Config/Project.local.xcconfig`, which is gitignored.

`fastlane/README.md` is autogenerated on every run and deliberately untracked.
